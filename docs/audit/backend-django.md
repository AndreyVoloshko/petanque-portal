# Backend And Django Usage Audit

## Summary

The app is recognizably Django and uses common Django features correctly at a high level: models, views, templates, forms, admin, migrations, management commands, and settings. The quality issues are in old patterns, manual validation bypasses, weak separation of concerns, and several misconfigured settings.

## Good Django Usage

- Domain models use Django ORM relationships (FK, M2M through models).
- Public pages are rendered through Django templates with base template inheritance.
- Admin classes, inline models, and custom actions are configured for operational workflows.
- Forms use Django Forms and crispy-forms for rendering.
- Authentication uses Django's auth system (`@login_required`, `authenticate()`).
- Named URL patterns enable `reverse()` throughout.
- Custom management command for rating recalculation.
- Migrations are complete (70 migrations including 1 data migration).
- Password validators are configured (4 standard validators).

## Non-Idiomatic Or Risky Django Usage

### Forms Override `is_valid()` Instead of `clean()`

**Files:**
- `forms/registration_team_form.py:58-87`
- `forms/registration_player_form.py`

Overriding `is_valid()` and directly mutating `self._errors` is non-idiomatic. Django validation should use `clean()`, `clean_<field>()`, and `add_error()`.

Impact: validation behavior is brittle, error format may not match Django's expectations, and the form skips some of Django's internal validation coordination.

### Deprecated Settings Still Present

**File:** `api/settings.py`

| Setting | Status | Replacement |
|---------|--------|-------------|
| `STATICFILES_STORAGE` | Deprecated Django 4.2 | `STORAGES["staticfiles"]` |
| `DEFAULT_FILE_STORAGE` | Deprecated Django 4.2 | `STORAGES["default"]` |
| `USE_L10N` | Deprecated Django 4.0 | Remove (default True) |

### `STATIC_ROOT` and `MEDIA_ROOT` Are URLs, Not Paths

**File:** `api/settings.py:206,210`

```python
STATIC_ROOT = STATIC_URL  # This is a URL like "//bucket.s3.amazonaws.com/static/"
MEDIA_ROOT = '//'+AWS_S3_CUSTOM_DOMAIN+'/'+MEDIAFILES_LOCATION+'/'
```

Django expects filesystem paths for `*_ROOT` settings. This breaks `collectstatic` and `django.contrib.staticfiles` system checks.

### Manual URL Redirects With Hardcoded Paths

Some views use hardcoded paths:
- `views/login.py:31`: `next_url = '/profile/'`
- `views/login.py:8`: `return HttpResponseRedirect('/profile/')`

Should use `redirect('profile')` with named URLs.

### Error Handling Is Broad

Bare exception patterns found:
- `api/settings.py:18`: `except:` (bare except, catches everything including SystemExit)
- `models/player.py:260`: `except Exception:` masks MultipleObjectsReturned
- `views/register.py:66`: `except Exception as e:` — shows raw exception to user
- `models/team.py:41,61`: broad catches in team logic

### `classmethod` With `self` Parameter

**File:** `models/player.py:147`, `models/tournament.py:361,397,409`

```python
@classmethod
def get_actual_players_list(self):  # Should be 'cls'
```

Works technically (Python doesn't enforce the name), but confusing and non-standard.

### Wildcard Import

**File:** `views/login.py:2`

```python
from django.http import *
```

Pollutes namespace, makes dependencies unclear.

### Old Django Comments

Settings file header still says:
```python
"""Generated by 'django-admin startproject' using Django 1.11.3."""
```

And references Django 1.11 docs in multiple comments. Not harmful but misleading.

### `STATICFILES_DIRS` Includes `MEDIA_ROOT`

```python
STATICFILES_DIRS = [
    os.path.join(BASE_DIR, "static/"),
    MEDIA_ROOT,  # This is a URL string, not a directory
]
```

This will either error or be silently ignored by Django's file finders.

## Recommended Improvements (Priority Order)

1. Fix `STATIC_ROOT`/`MEDIA_ROOT` to filesystem paths (breaks `collectstatic`).
2. Fix bare `except:` in settings (masks startup errors).
3. Move form validation into `clean()` methods.
4. Replace deprecated storage settings with `STORAGES`.
5. Replace hardcoded URLs with `redirect()` + named routes.
6. Replace broad exceptions with specific exception types.
7. Fix `classmethod` parameter naming.
8. Remove stale Django 1.11 comments.
9. Introduce service functions for multi-step domain workflows.
